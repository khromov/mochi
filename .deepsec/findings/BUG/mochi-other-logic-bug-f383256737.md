# [BUG] An abandoned send job permanently suppresses its own retry: the `sending` claim is never released, and the loss is logged as 'sent'

**File:** [`packages/support/src/newsletter/jobs.server.ts`](https://github.com/khromov/mochi/blob/main/packages/support/src/newsletter/jobs.server.ts#L41-L83) (lines 41, 42, 50, 73, 83)
**Project:** mochi
**Severity:** BUG  •  **Confidence:** high  •  **Slug:** `other-logic-bug`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

`claimNewsletterSend()` (L41) flips the row `pending → sending` via `UPDATE … WHERE id = ? AND email_status = 'pending'` (db.server.ts L136). Only two paths ever release that claim: a *thrown* send error, via `noteNewsletterAttemptError` → `email_status = 'pending'` (L78), and an admin resend, via `refreshConfirmToken` → `requeue` (db.server.ts L343). Abnormal job termination is neither — and it is reachable on an ordinary deploy. `packages/support/src/index.ts` never sets `queueShutdownTimeout`, so the graceful drain budget is the framework default `DEFAULT_QUEUE_SHUTDOWN_TIMEOUT = 10_000` ms (queue.ts L229); the framework's own test spells out the consequence: 'queueShutdownTimeout bounds the drain: a job outlasting it is left for retry, not blocked on' (queueWorker.test.ts L243). A cold SMTP delivery (DNS + TCP + TLS + AUTH + DATA to a third-party provider) routinely exceeds 10s — nodemailer's default connectionTimeout alone is 2 minutes — so a SIGTERM landing during a signup's first send abandons the job mid-`await` at L50 with the row still 'sending'. bun-boss then re-delivers the job after expireInSeconds (default 900), the retry reaches L41, `claimNewsletterSend` returns false because the row is no longer 'pending', and the processor writes `appendNewsletterLog(…, { event: 'sent', detail: 'Skipped — another job already handled this confirmation' })` and returns `{ sent: false }` — a *resolved* handler, so bun-boss marks the job completed and never retries again. Net effect: the subscriber's confirmation email is silently never delivered, the retry machinery that exists for exactly this case is disarmed by the stale claim, and the delivery log the admin panel renders records the loss under the **'sent'** event, making it undiagnosable. The row sits at `status='pending'`/`email_status='sending'` until `purgeExpiredSubscribers` (L97) deletes it after CONFIRM_TTL_MS, destroying the evidence. The same wedge fires if `markNewsletterEmailSent` (L83) throws, and on any SIGKILL/OOM. The test suite (newsletter.test.ts L321) exercises only the two designed release paths, so this is untested.

## Recommendation

Make the claim self-healing rather than permanent — claim on `(email_status = 'pending' OR (email_status = 'sending' AND claimed_at < now - staleMs))`, storing a `claimed_at` alongside the status, so a re-delivered job after an abandoned attempt re-acquires instead of skipping. Alternatively release the claim on the retry path by keying it to the attempt (`WHERE email_status = 'pending' OR claim_attempt < ?`). Separately: (1) stop logging a skip under `event: 'sent'` at L36 and L42 — add a distinct 'skipped' EmailLogEvent so the admin log cannot report an undelivered confirmation as sent; and (2) raise `queueShutdownTimeout` in index.ts above a realistic SMTP send duration (e.g. 30000) so an ordinary deploy drains in-flight sends instead of abandoning them.

## Revalidation

**Verdict:** true-positive

Every link in the chain verifies. `claim()` is `UPDATE … SET email_status='sending' WHERE id=? AND email_status='pending'` (db.server.ts L136), and the only releases are `noteAttemptError` (reachable solely from the inner catch when `Mochi.email` throws) and `requeue` (admin resend via `refreshConfirmToken`, L343) — abnormal termination is neither. packages/support/src/index.ts sets no `queueShutdownTimeout`, so `mountQueues` applies DEFAULT_QUEUE_SHUTDOWN_TIMEOUT = 10_000 (queue.ts L229, L1065), and the framework's own test asserts the consequence: after the budget expires the job is left not-completed (queueWorker.test.ts L243-280). bun-boss then recovers it — `supervise` defaults true at a 60s interval (attorney.ts L387, L642) and `failJobsByTimeout` re-inserts an `active` job past `started_on + expire_seconds` as `retry` while `retry_count < retry_limit` (plans.ts L1743, failJobsBody); this queue leaves `expireInSeconds` at the 900s default. The retry then reaches L41, `claimNewsletterSend` returns false because the row is still 'sending', and the processor logs `{ event: 'sent', detail: 'Skipped — another job already handled this confirmation' }` and resolves, so bun-boss completes the job and never retries: the confirmation is silently never delivered and the log labels the loss 'sent'. I am downgrading from HIGH_BUG for three reasons the write-up misses or overstates. The trigger needs an abnormal termination inside the seconds-wide claim→markSent window (SIGKILL/OOM/crash, or a SIGTERM with a send outlasting 10s — 'routinely exceeds 10s' overstates a typical SMTP delivery). It is not undiagnosable: EmailLogDialog renders the row's `email_status`, so the subscriber sits visibly at 'email sending', and the log detail says 'Skipped'. And there is a third release path the finding does not mention — a user re-submitting after the cooldown hits `subReArmStmt`, which resets `email_status='pending'` with a fresh token and enqueues a new job, so the affected person recovers by trying again. The stale-claim fix (a `claimed_at` staleness window) and the distinct 'skipped' log event are both still the right changes.
