# [BUG] A `</script` substring in a rune module silently disables the whole oxc dropped-call scan for that file

**File:** [`packages/mochi/src/compiler/oxcDroppedCalls.ts`](https://github.com/khromov/mochi/blob/main/packages/mochi/src/compiler/oxcDroppedCalls.ts#L86-L101) (lines 86, 101)
**Project:** mochi
**Severity:** BUG  •  **Confidence:** high  •  **Slug:** `other-logic-bug`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

For non-`.svelte` inputs, `scriptPrograms()` borrows Svelte's TS-aware parser by wrapping the entire user source in a script tag: `parse(`${prefix}${source}</scr`+`ipt>`)`. The HTML-layer script reader closes the block at the *first* `</script` in the wrapped text, so any occurrence inside the developer's own source — a string literal, a template literal, a comment — truncates the module. `findOxcDroppedCalls` is called with real user modules: `clientBuildLoaders.ts:54-62` registers an `onLoad({ filter: /\.svelte\.[jt]s$/ })` handler that passes `original` (the untranspiled author source) to `onCompiled`, which is `warnOxcDroppedCalls` (ComponentRegistry.ts:1331, 684). Concretely, a `foo.svelte.ts` containing `export const sample = '<script>init()</script>';` wraps to `<script module lang="ts">export const sample = '<script>init()</script>';…</script>`; the module body ends at `'<script>init()` — an unterminated string literal — so acorn throws, the `catch` at line 102-105 swallows it as "the compiler reports the real syntax error" (it won't: the file compiles fine), and `[]` is returned. Every `$effect`/`$derived.by` in that file goes unscanned. That matters because this diagnostic is the only thing standing between a developer and a silently non-reactive effect: the whole premise of the file is that oxc deletes `String(items);` inside an `$effect`, killing the subscription with no error at build or runtime. Losing the warning means shipping an island whose effect never re-runs. This is a correctness/DX bug only — the input is the developer's own source, so there is no security impact. Note the `.svelte` branch (line 80-81) is unaffected, since Svelte's own parser handles the real file. Also worth noting: the `visit`/`check` walk at line 107-145 runs *outside* the try/catch that only covers `scriptPrograms`, so any throw there escapes a Bun `onLoad` handler and fails the user's client build — unlike the sibling barrel diagnostic, which the author deliberately wrapped (`ComponentRegistry.ts:1964-1989`, "must never break a build").

## Recommendation

Neutralize the sequence before wrapping, using an equal-length replacement so every AST offset and the `line` computation at line 120 stay valid: `source.replaceAll('</script', '<!script')` (both 8 chars; `</script` cannot legally appear in JS outside a string/template/regex, and the literal's *contents* are irrelevant to this diagnostic). Better still, drop the HTML round-trip for non-`.svelte` inputs and parse the module directly with the acorn-typescript parser Svelte already depends on. Separately, move the `visit(program, null)` loop inside the try/catch (or wrap the `findOxcDroppedCalls` call in `warnOxcDroppedCalls`) so an advisory warning can never fail a build.

## Revalidation

**Verdict:** true-positive

Confirmed end-to-end by reading Svelte 5.57.3's own parser. `scriptPrograms()` (oxcDroppedCalls.ts:85-87) wraps a non-`.svelte` source in `<script module lang="ts">…</script>` and hands it to `parse()`. In `svelte/src/compiler/phases/1-parse/read/script.js:11,25`, `regex_closing_script_tag = /<\/script\s*>/` is fed to `Parser.read_until_regex` (1-parse/index.js:282-298), which returns the slice up to the **first** match in the remaining template. So any complete `</script>` sequence in the developer's own module — in a string, template literal, or comment — truncates the wrapped text at that point. The call path to real user modules is real: `registerSvelteModuleLoader` (clientBuildLoaders.ts:54-62) registers `onLoad({ filter: /\.svelte\.[jt]s$/ })` and passes `original` (the untranspiled author source) to `onCompiled`, which ComponentRegistry.ts:1331 binds to `warnOxcDroppedCalls` → `findOxcDroppedCalls` (line 684-685). The truncated text then either fails acorn (swallowed by the `catch` at lines 102-105, whose comment — 'the compiler reports the real syntax error' — is wrong here, since the real file compiles fine) or, when the truncation lands in a comment, parses as a valid but empty/partial Program. Either way the function returns no findings, so every `$effect`/`$derived.by` in that file goes unscanned and a silently non-reactive effect ships with no warning — which is the entire purpose of this diagnostic (`oxcDroppedCalls.test.ts:247-255` proves rune modules are a first-class scan target via the `tracker.svelte.ts` fixture). One imprecision in the write-up: truncation requires the full `</script>` (the regex demands the `>`), not a bare `</script` substring; the concrete example given satisfies this. The suggested 8-for-8-char replacement (`</script` → `<!script`) does preserve every AST offset and the `line` computation at line 120. The secondary observation that `visit()` (lines 107-145) sits outside the try/catch, unlike the deliberately-wrapped sibling diagnostic (ComponentRegistry.ts:1964-1989, 'must never break a build'), is structurally accurate, though I found no realistic throw path there — callee/identifier names are the only regex inputs and are escaped. Correctness/DX only, as the finding itself states: the input is the developer's own source, so there is no attacker-controlled surface. BUG is the right severity.
