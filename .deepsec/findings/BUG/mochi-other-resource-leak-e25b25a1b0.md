# [BUG] Module-scoped SQLite store leaks a DB connection and a timer on every dev reload (no pinGlobal, and ownsStore=false blocks framework cleanup)

**File:** [`packages/site/src/demos/rate-limit/routes.ts`](https://github.com/khromov/mochi/blob/main/packages/site/src/demos/rate-limit/routes.ts#L6-L11) (lines 6, 7, 11)
**Project:** mochi
**Severity:** BUG  •  **Confidence:** high  •  **Slug:** `other-resource-leak`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

rateLimitSqliteStore({ path: './db/rate-limit.sqlite' }) is evaluated at module scope (line 7). hitlimit's BunSqliteStore constructor opens a bun:sqlite Database in WAL mode, prepares 10 statements, and starts a 60-second setInterval cleanup timer - all OS-level resources. Two independent code paths make this leak: (1) Dev reload. devWatcher.ts's buildEntry() bundles the whole server entry graph with packages: 'external' (so first-party modules like this one are inlined) and then calls extractServeOptions(outFile, { fresh: true }), re-executing every module top level. isServerEntryDep() routes any non-.svelte change in that graph to triggerEntryReload, so editing any server-side site file re-runs lines 6-7 and constructs a brand-new Database plus a brand-new 60s interval. The framework documents this precisely - devWatcher.ts:83-86: 'Each entry reload re-evaluates the whole first-party module graph, so a module-scoped resource (a DB pool, a timer, an SMTP pool) is re-created and the old one orphaned with its handle still open', and dev/consoleLogger.ts:421 tells the user to 'hold them with pinGlobal()'. (2) The framework cannot clean it up. Because store is passed in explicitly, createRouteLimiter sets ownsStore: false (rateLimit.ts:239). Both cleanup paths in Mochi.ts are gated on that flag: retireLimiter() only calls limiter.store.shutdown?.() if (limiter && limiter !== sharedGlobalLimiter && limiter.ownsStore) (Mochi.ts:838), and server.stop()'s sweep iterates rateLimitStores, which buildLimiter only populates if (limiter.ownsStore) (Mochi.ts:809-811). So updateRouteLimiter -> retireLimiter -> resolveLimiter swaps in the new limiter while the previous store is silently orphaned, connection open and timer running. A route whose rateLimit omits store (framework-owned) is correctly torn down - this demo showcases the one configuration that cannot be. Result: after N reloads there are N open SQLite connections (holding .sqlite, -wal and -shm descriptors) and N live timers, all issuing DELETE statements against the same file every 60s. On Windows the stale handles prevent unlinking the db file - the same hazard rateLimit.ts's own shutdown shim (lines 131-163) exists to avoid. The framework's recompile:module-churn warning fires at reload 10, but only logs. This is also the one module-scoped OS resource in packages/site not held with pinGlobal(): lib/blog.ts:30, lib/docs.ts:55 and lib/highlight.server.ts:68 all use it. And since this file is published verbatim as reference source (rendered on the demo page via files.ts and served at /demos/rate-limit/llms.txt), it teaches the leaking form to readers who copy it into real apps. Not a security issue: devWatcher runs only in development, and the shutdown-path leak is masked because installShutdownHandlers calls process.exit(0) after performShutdown.

## Recommendation

Hold the store with the framework's documented idiom so a dev reload reuses the existing connection instead of opening another: wrap it in pinGlobal, e.g. const store = pinGlobal('mochi-site:rate-limit-store', () => { mkdirSync('./db', { recursive: true }); return rateLimitSqliteStore({ path: './db/rate-limit.sqlite' }); }); importing pinGlobal from 'mochi-framework'. This also makes the published demo model the correct pattern. Separately, consider having Mochi.serve() shut down caller-supplied stores on server.stop() (or expose an opt-in flag), since ownsStore: false currently means a user-owned store is never closed on any path - or document that a mochi:shutdown hook is the caller's responsibility.

## Revalidation

**Verdict:** true-positive

I verified every link in the chain, including the third-party internals. routes.ts:7 calls `rateLimitSqliteStore({ path: './db/rate-limit.sqlite' })` at module scope; that delegates to hitlimit's `sqliteStore`, whose `BunSqliteStore` constructor does `new Database(path)`, `PRAGMA journal_mode = WAL`, three CREATE TABLEs, ten `db.prepare(…)` and `setInterval(…, 60000)` (node_modules/@joint-ops/hitlimit-bun/dist/stores/sqlite.js:19-66) — all OS-level handles, and its `shutdown()` is the only thing that clears them. Because the store is passed in explicitly, `createRouteLimiter` sets `ownsStore: !options.store` → false (rateLimit.ts:239), and both framework cleanup paths are gated on that flag: `buildLimiter` adds to `rateLimitStores` only `if (limiter.ownsStore)` (Mochi.ts:809-811), and `retireLimiter` calls `limiter.store.shutdown?.()` only `if (limiter && limiter !== sharedGlobalLimiter && limiter.ownsStore)` (Mochi.ts:838-845). So this store can never be closed by either the dev-reload retirement or the `server.stop()` sweep. The reload trigger is real: `isServerEntryDep` (devWatcher.ts:79) routes any non-`.svelte` entry-graph change to `triggerEntryReload` → `buildEntry()`, which bundles with `packages: 'external'` (so first-party modules like this one are inlined) and then calls `extractServeOptions(outFile, { fresh: true })`; `freshImport` writes a uniquely-named artifact and imports it (compiler/freshImport.ts), so every module top-level re-executes and lines 6-7 construct a brand-new Database plus a brand-new 60s interval. devWatcher.ts:82-86 documents precisely this hazard and `reachedModuleChurnThreshold` only logs at reload 10. `pinGlobal` is the prescribed idiom and is used by lib/blog.ts:30, lib/docs.ts:55 and lib/highlight.server.ts:68; I grepped packages/site and this is indeed the only module-scoped OS resource not held that way (the only other `setInterval`s are per-stream inside the streams demo's SSE handlers). Dev-only, and I confirmed the shutdown-path leak is masked by `process.exit(0)` after shutdown (Mochi.ts:2214) — so no security impact, but the file is published verbatim as reference source and models the leaking form. BUG is correct.
