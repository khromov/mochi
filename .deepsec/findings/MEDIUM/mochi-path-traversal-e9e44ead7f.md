# [MEDIUM] Tar entry names are joined onto the output directory with no containment check (tar slip)

**File:** [`packages/cli/src/download.ts`](https://github.com/khromov/mochi/blob/main/packages/cli/src/download.ts#L39-L57) (lines 39, 40, 41, 42, 57)
**Project:** mochi
**Severity:** MEDIUM  •  **Confidence:** medium  •  **Slug:** `path-traversal`

## Owners

**Suggested assignee:** `stanislav.khromov+github@gmail.com` _(via last-committer)_

## Finding

extractTemplate() enumerates the downloaded tarball with `Bun.Archive(...).files()` and writes each entry with `Bun.write(path.join(dir, relative), file)`. `relative` is derived purely by slicing a fixed prefix length off the archive-supplied entry name (L40-41) and is never validated. Bun's documented path hardening — rejecting absolute paths and normalizing away `..` — applies to `Bun.Archive#extract()`, NOT to `.files()`; the Bun docs explicitly say to validate `.files()` paths yourself before writing. This loop therefore opts out of that protection. An entry named `mochi-main/packages/minimal/../../../../../../.ssh/authorized_keys` matches the `*/${subdir}/**` glob (the package's own test proves dot-prefixed segments match, since `.gitignore` is extracted), yielding `relative = '../../../../../../.ssh/authorized_keys'` and a `path.join` that escapes the scaffold directory — arbitrary file write with the user's privileges, i.e. RCE via `~/.zshrc`, `~/.ssh/authorized_keys`, or a Claude/editor settings file, before the user ever inspects or runs the scaffold. On Windows, backslash segments in an entry name (`a\..\..\x`) escape through `path.win32.join` as well. Exploitability is gated on controlling the archive bytes: the URL is HTTPS to codeload.github.com and git trees cannot store `..` components, so a plain repo-write attacker cannot plant such an entry — but a TLS-intercepting proxy (corporate MITM with a trusted root CA, or a hostile `HTTPS_PROXY` that Bun's fetch honours), or any future change that lets a user/third party supply a `source` (the generic `<owner>/<repo>/<subdir>#<ref>` parser is already written for it), makes it live. `fetch` at L57 also uses the default `redirect: 'follow'`, widening who can serve the bytes. Note this is the exact pattern the repo's own review guidance asks to flag: 'archive extraction that joins an entry name onto an output directory (packages/cli/src/download.ts) without rejecting `..` segments'.

## Recommendation

Validate each entry before writing: reject `relative` if it is empty, if `path.posix.normalize(relative)` starts with `..`, if any segment equals `..`, or if it contains a backslash; then assert containment with `const target = path.resolve(dir, relative); if (target !== dir && !target.startsWith(dir + path.sep)) throw ...`. Add a test with a fixture entry named `mochi-HEAD/packages/minimal/../../escaped.txt` asserting nothing is written outside `dir`. Also pass `redirect: 'error'` to the fetch at L57, and consider pinning `Template.source` to a tag/commit (the field already supports `#<ref>`) so the npm-provenance guarantee on the published CLI extends to the template bytes it writes.

## Revalidation

**Verdict:** true-positive

The missing control is real and the mechanism is confirmed from Bun's own documentation and typings, not inferred. `/docs/runtime/archive` attaches its security note explicitly to extraction ('Bun.Archive validates paths during extraction… normalizes away path traversal components (`..`)'), while the `files()` JSDoc in `node_modules/bun-types/bun.d.ts` promises only that keys are 'file paths (always using forward slashes `/` as separators)' — no absolute-path rejection, no `..` normalization — and the docs' own 'additional security with untrusted archives' example tells you to enumerate `files()` and validate the paths yourself. `extractTemplate` (download.ts:33-46) does none of that: `root` is the entry's own first segment, `relative` is a fixed-length slice, and `Bun.write(path.join(dir, relative), file)` writes it unchecked, so an entry `mochi-HEAD/packages/minimal/../../../../x` matches the `*/packages/minimal/**` glob (the suite's own fixture proves dot-prefixed segments survive the glob, since `.gitignore` is extracted) and escapes `dir`. I confirmed the slice arithmetic itself is sound and that no caller-side validation exists anywhere in cli.ts/create.ts/utils.ts, and that no fix has landed (last commit touching these files predates the finding). Exploitability is genuinely gated, as the finding concedes: `tarballUrl()` hardcodes HTTPS to codeload for a hardcoded `khromov/mochi/...` source (templates.ts:14-27, and cli.ts restricts `--template` to the two known ids), and git trees cannot hold a `..` path component, so neither a repo-write attacker nor a malicious PR can plant such an entry — it needs control of the archive bytes (TLS-intercepting corporate proxy with a trusted root, CA mis-issuance, CDN compromise) or a future user-supplied `source`, which the generic `<owner>/<repo>/<subdir>#<ref>` parser is already written for. Two sub-claims are weaker than stated: the Windows backslash variant is probably moot because `files()` keys are documented as always forward-slashed, and in a bytes-controlling-MITM scenario the attacker already gets code execution from the scaffold itself (the CLI's outro tells the user to run `bun install && bun run dev`), so writing outside `dir` buys stealth and persistence rather than new capability. I keep MEDIUM because the project's stated threat model treats the create-mochi tarball as an untrusted supply-chain input and its own review guidance names this exact pattern ('archive extraction that joins an entry name onto an output directory… without rejecting `..` segments'), and it is not in the known-false-positive list. The recommended fix (normalize + reject `..`/absolute, assert containment with `path.resolve`, plus a fixture test) is cheap and correct.
