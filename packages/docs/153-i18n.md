## Internationalization (i18n)

Mochi has a first-class integration with [Wuchale](https://wuchale.dev), a compile-time i18n library. You write plain text in your components; Wuchale extracts it into catalogs and replaces each string with an indexed runtime lookup — no string keys ship to the browser. Mochi hosts Wuchale's transform on its own Bun build (no Vite) and resolves the active locale per request.

### Install

```sh
bun add wuchale @wuchale/svelte
```

### Configure Wuchale

Create `wuchale.config.js` in your project root. Use `loader: 'custom'` — Mochi generates the loaders for you.

```js
// @ts-check
import { defineConfig } from 'wuchale';
import { adapter as svelte } from '@wuchale/svelte';

export default defineConfig({
  locales: ['en', 'sv', 'uk'],
  localesDir: './src/locales',
  adapters: {
    main: svelte({ loader: 'custom', files: ['src/**/*.svelte'] }),
  },
});
```

### Enable it in `Mochi.serve()`

```ts
Mochi.serve({
  // …
  i18n: {
    locales: ['en', 'sv', 'uk'],
    sourceLocale: 'en',
    resolveLocale: (event) => /* return a locale id or undefined */,
  },
});
```

`resolveLocale` runs per request inside the request context, so `getRequestContext()` (cookies, url, …) is available. Return one of your `locales`, or `undefined` to fall back to `sourceLocale`.

### Write translatable code

Just write text. No wrappers, no keys.

```svelte
<h1>Hello, Mochi speaks your language</h1>
<button>Clicked {count} times</button>
```

<Callout type="info">

Extraction only runs on `.svelte` files (the ones matched by your adapter's `files`). Strings in plain `.ts`/`.js` modules are not translated.

</Callout>

### Extract & translate

The loaders Mochi generates must exist before the Wuchale CLI runs, so start the dev server once, then extract:

```sh
bun run dev          # Mochi writes src/locales/main.loader*.svelte.js on boot
bunx wuchale         # extract strings → src/locales/{en,sv,uk}.po
```

Fill in the `msgstr` lines in the non-source `.po` files, then run `bunx wuchale` again to compile the catalogs. Commit the `.po` files (your translations) and `wuchale.config.js`. The generated `.wuchale/` directory, the loaders, and `data.js` are derived from the `.po` files and regenerated by `mochi-framework build` and dev — gitignore them:

```
**/locales/.wuchale/
**/locales/*.loader.svelte.js
**/locales/*.loader.server.svelte.js
**/locales/data.js
```

<Callout type="warning">

In production Mochi runs the transform against the **committed** catalogs. After adding or changing strings, re-run `bunx wuchale` (and restart) — otherwise new strings fall back to the source locale.

</Callout>

<Callout type="info">

Because the loaders are gitignored, a fresh checkout (e.g. CI) has nothing for `tsc`/`svelte-check` to resolve when a component imports `./locales/main.loader.svelte.js`. Run [`mochi-framework prepare-i18n`](/docs/cli#prepare-i18n) before your typecheck to generate them without a full build:

```json
{
  "scripts": {
    "typecheck": "mochi-framework prepare-i18n && svelte-check && tsc --noEmit"
  }
}
```

</Callout>

## How locales reach the browser

The interesting part is hydration: a hydrated island must render the **same** language on the client that it rendered during SSR.

Mochi generates two loaders into your `localesDir`:

- **Server loader** — reads the locale from `getRequestContext().locals.locale` (which the i18n middleware sets from your `resolveLocale`). SSR renders in that language.
- **Client loader** — reads `window.__mochi_locale__` (Mochi seeds it into every page `<head>`) and calls `loadLocaleSync()` synchronously at import, so islands hydrate with the matching strings — no flash, no mismatch. It also exports `setLocale(locale)` for switching the locale in place.

You don't edit these loaders; they are regenerated on boot.

## URL-based locales

Put the locale in the path and let navigation do the switching — each language gets its own shareable, indexable address. Define static routes for the source locale and a `:lang` variant for the rest (static routes win over the param route in Bun's matcher):

```ts
// routes.ts
'/':        Mochi.page('./src/Home.svelte'),
'/about':   Mochi.page('./src/About.svelte'),
'/:lang':       Mochi.page('./src/Home.svelte'),
'/:lang/about': Mochi.page('./src/About.svelte'),
```

```ts
// serve()
i18n: {
  locales: ['en', 'sv', 'uk'],
  sourceLocale: 'en',
  resolveLocale: ({ url }) => {
    const seg = url.pathname.split('/')[1] ?? '';
    return ['sv', 'uk'].includes(seg) ? seg : 'en';
  },
},
```

A language switcher is just links to `/`, `/sv`, `/uk`. Switching navigates, so every page is freshly server-rendered in the chosen language.

## Cookie-based locales (switch in place)

Store the locale in a cookie and switch the language **without a reload** by calling the generated `setLocale()` from a hydrated island:

```ts
// serve()
i18n: {
  locales: ['en', 'sv', 'uk'],
  sourceLocale: 'en',
  resolveLocale: () => getRequestContext().cookies.get('locale') ?? 'en',
},
```

```svelte
<!-- inside a mochi:hydrate island -->
<script lang="ts">
  import { cookies, isBrowser } from 'mochi-framework';
  import { setLocale } from './locales/main.loader.svelte.js';

  function choose(code: string) {
    setLocale(code); // re-translates this island instantly (all locales are bundled)
    if (isBrowser) cookies.set('locale', code, { expires: 365, path: '/' });
  }
</script>
```

`setLocale()` swaps the reactive catalog, so the island re-renders immediately; the cookie keeps the choice for the next SSR render. Translatable content you want to switch live should live inside the hydrated island.

<Callout type="info">

Both patterns are shown end-to-end in the demos: the URL-based demo and the cookie-based **Internationalization (cookies)** demo on the [demos page](/docs/demos).

</Callout>
