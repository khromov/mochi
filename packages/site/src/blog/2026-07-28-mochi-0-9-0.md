# Mochi 0.9.0

Mochi 0.9.0 is out, with 26 commits since [0.8.0](https://github.com/khromov/mochi/blob/main/packages/mochi/CHANGELOG.md). It's a smaller release than the last one, and one change is breaking — if you deploy a prebuilt app, read [Relocatable builds](#relocatable-builds) before upgrading.

## Faster builds with rsvelte

[rsvelte](https://github.com/baseballyama/rsvelte) is a Rust port of the Svelte 5 compiler built on [OXC](https://oxc.rs/). Mochi can now route component compilation through it instead of the JavaScript `svelte/compiler`. It's [opt-in](/docs/rsvelte/):

```sh
bun add -d @mochi-framework/rsvelte
```

```ts
await Mochi.serve({
  port: 3000,
  svelteCompiler: 'rsvelte',
  routes,
});
```

On our `demos` benchmark that takes a cold build from 384ms to 289ms (−25%), with the SSR build itself down 36%. You can A/B it without touching your config using `MOCHI_SVELTE_COMPILER=rsvelte bun run build`, and Mochi logs the backend it resolved at boot. This site runs on it.

Only `compile()` and `compileModule()` go through rsvelte — parsing and preprocessing stay on the official compiler, because Mochi's island preprocessor walks a real Svelte AST, so `mochi:hydrate`, `mochi:defer` and your own preprocessors behave exactly as before. Two caveats: rsvelte is pre-1.0, and there are no musl binaries, so Alpine images fall back to `svelte/compiler`.

## Request cache

[`requestCache()`](/docs/request-cache/) memoizes work for the duration of a single HTTP request. A page that renders the same lookup in ten components pays for it once, and the next request always sees fresh data.

```ts
import { requestCache, requestMemo } from 'mochi-framework';

const user = await requestCache(`user:${id}`, () => db.user(id));

// Or wrap once at module scope — every importer shares the memo.
export const getUser = requestMemo((id: string) => db.user(id));
```

Both forms store the in-flight promise, so concurrent callers share one execution instead of racing, and a rejection evicts the entry so failures are never cached. It isn't a `MochiCache` replacement — there's no TTL, no backend and no eviction; it's the short-lived layer that sits in front of one. The debug bar's **Cache** panel gained a Request cache section showing hits, misses and hit rate for the current request.

## Relocatable builds

Build output no longer contains a single absolute path. Artifacts are stored relative to the out-dir and resolved against the manifest's own directory, and island identity is derived from project-relative source paths — so the same commit built on any machine produces identical island names, bundle filenames and SSR'd HTML. Build in a CI stage, copy `.mochi/` into the final image, rename the directory, and boot from wherever it landed:

```ts
Mochi.serve({ manifest: '/srv/app/build/manifest.json' });
```

<Callout type="danger">

**Two things to do when you upgrade.** Re-run `mochi-framework build` — the manifest schema version is now an exact gate, and a build made by a different `mochi-framework` version throws at startup instead of half-loading. And **ship your `public/` directory** with production deploys: the build no longer copies it into the out-dir, so an image that carries only `.mochi/` and `src/` will 404 every static file. Keep `public` out of your `.dockerignore`.

</Callout>

To make that second one loud rather than silent, the build records how many files it saw in `publicDir`, and a server that boots to an empty one now warns with the count instead of quietly serving 404s. See [Relocatable builds](/docs/deployment-options/#relocatable-builds) for the remaining constraints.

## Other improvements

- **Captcha** — [`<MochiCaptcha />`](/docs/captcha/) no longer hangs on slow mobile browsers: the proof-of-work now uses synchronous SHA-256, surfaces every failure as a retry button, and resumes the nonce search rather than starting over. Difficulty and patience are configurable through the `captcha:bits` and `captcha:solveBudgetMs` filters, and the widget reserves its own space during SSR so hydration causes no layout shift.
- **Extensions** — pulling a server-only framework module (hooks and filters, config, request context) into a client bundle now fails the build with a message naming the file that imported it. Previously a filter that reached the browser silently returned the framework default. See [server-only modules](/docs/extensions/#server-only).
- **Svelte Shaker** — [`optimize`](/docs/svelte-shaker/) now requires `svelte-shaker` 0.18.1 or newer. Older versions stripped unknown-namespace attributes, which silently removed `mochi:` directives from the shaken source — an island would still render, it just never hydrated. Fixed upstream, pinned here, and covered by a regression test.
- **Testing** — a memlab heap-snapshot analyzer for chasing leaks, plus property-based fuzzing suites over the crypto, cookie, CSRF and form-action code that run as part of the normal test run.
- **Housekeeping** — source comments slimmed down, dependencies bumped across the monorepo.

## Install or upgrade

New project:

```sh
bun create mochi@latest my-app
```

Existing project — bump the dependency and restart the dev server:

```sh
bun add mochi-framework@latest   # or @0.9.0 to pin
bun run dev
```

If you code with an AI assistant, don't forget to add or refresh the [agent skill](/docs/docs-for-llms/). Copy the line for the agent you use:

```sh
bunx mochi-framework update-skill              # claude-code (default)
bunx mochi-framework update-skill opencode
bunx mochi-framework update-skill antigravity  # alias: agy
bunx mochi-framework update-skill codex
```

The [full changelog](https://github.com/khromov/mochi/blob/main/packages/mochi/CHANGELOG.md) has everything else. Mochi is still early and in alpha — if something breaks, [Discord](/discord/) or a [GitHub issue](https://github.com/khromov/mochi/issues) both work.
